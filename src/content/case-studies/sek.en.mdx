## The problem

I'm an apprentice in the office of a school with **around 535 students**, from preschool to high
school. Day-to-day work ran on **loose Excel spreadsheets and Word documents**, spread across several
systems: the academic one (a desktop app), the admissions tool, the state's digital school records,
the cafeteria system.

Re-enrollment, missing documents, contracts, official letters, scholarships, billing, pickup
authorizations... each lived in a different file, and none knew the others existed. Every task
started with a hunt for the right spreadsheet.

## Where I come in

A **personal project I started on my own**, built solo: requirements, architecture, code, tests,
docs and installation. I use **Claude Code as a pair programmer**, with a living handoff document
(decisions, pitfalls, roadmap) so each session picks up where the last one stopped.

## The rules of the game

This setup had more restrictions than a speedrun:

- **No IT staff** and regular Windows PCs, with no guarantee of being allowed to install software.
- **It has to work offline**: the school network isn't reliable.
- **Data about minors**: privacy (Brazil's LGPD) outweighs any convenience.
- **Several people at once**: one PC becomes the server and the others connect through the browser.
- **Integration through exports only**: with no guaranteed access to the academic system's database,
  data comes in through the `.xlsx` files it already exports.
- **Whoever maintains it may not code**: installing and updating must take two clicks.

## Details I'm proud of

### The conflict, in the real code

The screen sends the version it loaded. If someone else saved afterwards, the server answers **409**
with the name and time. In the browser, only the changed fields are sent, so if each person edited a
different field, both changes stay. (The code is in Portuguese on purpose: it's made by and for a
Brazilian school office.)

```js title="app/server.js"
function conferirVersao(atual, b, u) {
  const versao = b._versao,
    forcar = b._forcar;
  delete b._versao;
  delete b._forcar;
  if (versao === undefined || forcar) return;
  if ((atual.atualizado_em || null) === (versao || null)) return;
  if (!atual.atualizado_por || atual.atualizado_por === u.login) return;
  // ...looks up the name of whoever saved it
  falha(409, `${nome} alterou isto enquanto você editava.`, {
    conflito: { por: nome, em: atual.atualizado_em },
  });
}
```

### An encrypted backup that fits in your pocket

The backup runs with the system open (`VACUUM INTO`) and, with a password set, comes out encrypted
with **AES-256-GCM**: a key derived with `scrypt`, a random salt and IV, and a marker at the start to
recognize the file. Restoring takes two steps: validate, schedule, and only swap the database on the
next startup, keeping a copy of the old one.

```js title="app/lib/backup.js"
function cifrar(dados, senha) {
  const sal = crypto.randomBytes(16);
  const iv = crypto.randomBytes(12);
  const chave = crypto.scryptSync(senha, sal, 32);
  const c = crypto.createCipheriv("aes-256-gcm", chave, iv);
  const corpo = Buffer.concat([c.update(dados), c.final()]);
  return Buffer.concat([MARCA, sal, iv, c.getAuthTag(), corpo]);
}
```

### What else protects the data

- **Per-person login** with roles, a forced password change on first login, a server-enforced screen
  lock and a Content Security Policy.
- **Sessions in the database** (only the token hash): restarting the server logs nobody out. If it
  goes down, an "offline" banner shows up and **whatever was typed becomes a recoverable draft**.
- **Privacy (LGPD)**: a log of who opened each record, an export of everything about a student, and
  disposal that anonymizes former students while keeping the statistics.
- **Real data never reaches Git**: templates are scrubbed by a script before any commit, and tests
  run against a demo with fictional data.

Tasks like issuing school transcripts, tracking missing documents and building organization
spreadsheets, which took hours or days, now take a few minutes. That's still what the team reports,
not a formal measurement. The system is on version **5.8.x**, with about **875 KB of JavaScript** and
no framework, plus a home-grown test suite that takes the server down for real, simulates two people
editing at once, restores backups and checks all 30 screens.

## If I did it again

**I'd run a pilot first.** I built four stages before a single module ran on real data. Today I'd
start with **one module in a two-week pilot**: that's what proves value and earns the trust of
whoever decides.

Next steps: **measure the time** each task takes before and after, to turn the team's account into
numbers, and keep evolving from what the office uses most.

And what I decided **not** to do: rewrite it in React (months lost to gain a build step and
dependencies), move it to the cloud (minors' data on the internet) and automate bulk WhatsApp
messages (the official API is paid, and unofficial ones get the school's number banned).
