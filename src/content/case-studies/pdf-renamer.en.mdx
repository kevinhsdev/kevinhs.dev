<Tldr>
  I built a tool that reads scanned PDFs and suggests the right name for each one. Result: the
  office went from **~100 to ~300 documents a day**, and a class that took 3 days now takes 1 at
  most.
</Tldr>

## The problem

Picture opening a PDF called `scan_0412.pdf`, reading until you figure out it's an ID card, typing
`RG_2026.pdf`, finding the student's folder and saving. Now do that **200 times**, roughly one class.
That was **3 days** of work.

And it wasn't just slow. Hand-typed names get messy ("Ficha medica", "FICHA MÉDICA",
"ficha_saude"), and a file saved in the wrong folder simply vanishes from the student's record.

## Where I come in

I work in that office, so I felt the problem first-hand. I did it all on my own: spotted the
bottleneck, designed the flow, wrote the code and followed how it was used. Today the team uses it
**every day**.

## The rules of the game

No easy way out here. I had four limits to respect:

- **No installing software**: it had to run in the school computers' browser.
- **Files are local**: student records live in Windows folders, not on a server.
- **Lots of PDFs are just images**: scanned, with no searchable text.
- **The users don't code**: document types change by department, so tuning it couldn't depend on me.

Two smaller choices that still make a daily difference: the **File System Access API** saves
straight into the student's folder (Firefox falls back to a normal download), and **IndexedDB**
remembers the chosen folder, so nobody has to find it again every session.

## Details I'm proud of

### The classifier fits on one screen

The text is normalized (no accents, all caps), each type adds up the weights of the words it found,
and the winner is only suggested if it passes the threshold. That's it. No magic.

```js title="js/script.js (abridged)"
function scoreKeyword(text, kw) {
  // termos curtos exigem palavra inteira (evita "RG" casar dentro de outra palavra)
  if (kw.length <= 3) return new RegExp("\\b" + kw + "\\b").test(text);
  return text.includes(kw);
}

function classify(text) {
  const t = normalizeText(text);
  let best = null,
    bestScore = 0;
  for (const rule of CLASSIFY_RULES) {
    let score = 0;
    for (const [kw, w] of rule.kw) if (scoreKeyword(t, kw)) score += w;
    if (score > bestScore) {
      bestScore = score;
      best = rule.type;
    }
  }
  return bestScore >= CLASSIFY_THRESHOLD ? { type: best, score: bestScore } : null;
}
```

The default rules live alongside the ones the team creates: a department adds a word with a weight
and it applies right away.

### Built for people who use it all day

- **Duplicates**: if the name already exists in the folder, the tool asks and suggests a free number.
- **Keyboard**: shortcuts to confirm, skip and navigate, without leaving the keyboard mid-batch.
- **CSV history** of everything that was renamed.

### And there's AI too

In the version the office uses, the whole PDF goes to the **Anthropic API (Claude)**, which reads the
document and suggests the name. If there's no suggestion, the person picks the type from a list and
the file stays open to check. The public repository shows the OCR-and-rules version; the API
integration isn't in it.

## If I did it again

`script.js` has about a thousand lines in one file. It works, but I'd split it into modules
(classifier, files, viewer). And I'd build a set of fake PDFs to **measure the hit rate** after every
rule change, instead of eyeballing it.
